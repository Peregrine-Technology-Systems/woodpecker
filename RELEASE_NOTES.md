- test: de-flake the `agent/rpc` WebSocket client tests that failed ~2/3 of CI runs (#325). Every flaky test wrote the frame the client was waiting for (an ack, a `registered`/`task.assign` reply, a version push) and then did a fixed `time.Sleep(100ms)` before the handler returned and `defer conn.Close()` severed the socket. Under CI-VM CPU contention the client's readPump could be scheduled >100ms late, so the close raced — and beat — the just-written frame, and the client surfaced "connection lost" instead of the semantic reply (e.g. `"connection lost during registration" does not contain "denied"`). Replaced the fixed sleep at all 10 keep-alive sites with a `holdUntilCleanup` channel the mock server blocks on until the test finishes, so the connection stays fully open through the client's read — deterministic, no wall-clock bet. A second, separate flake class was also fixed: several deterministic round-trips (Version/Next/SendWithRetry/RegisterAgent/InitDoneUpdate) were bounded by a 5s context deadline that scheduling starvation on a contended CI VM could exceed even though the op completes in sub-millisecond wall-clock; these now share one documented `wsTestDeadline` (30s) constant that keeps a genuine hang detectable while giving a starved VM ample slack. The root starvation source was then fixed in `pts-test.sh`: `agent/rpc` (the only package doing real WebSocket round-trips) now runs in its own `go test` invocation instead of concurrently with the six other package binaries — on a constrained CI spot agent that cross-package competition starved its `readPump` goroutine past the timeouts. Reproduced locally under CPU saturation (bundled invocation flaked 2/3; isolated invocation passed 7/7). Verified with 50× full-package `-race` runs under `GOMAXPROCS=1`. Test/CI-only; no server/agent binary change.
- fix: `getTagCommitSHA` no longer loops forever when a release tag is not on the first `ListTags` page (#324). The tag-resolution loop (used for `release` events) never advanced its page counter, so a repo with >30 tags where the released tag sorted past page 1 sent the webhook-synchronous handler into a hot infinite loop re-fetching page 1, never finding the tag and never returning. Extracted the pagination into `resolveTagSHA`, which advances off the response's `NextPage` and terminates when the listing is exhausted (returning a "could not find tag" error instead of hanging). Covered by a page-2-hit test plus an anti-hang test that fails under a deadline if the loop ever regresses.
- fix: transient forge-API failures no longer permanently strand a CI trigger (#319, #318, #321). Two paths shared the same defect — a single unretried forge call whose momentary failure (GitHub 5xx / rate-limit / timeout) became terminal. **(1) Config-load (#319/#318):** the existing config-fetch retry loop fired with *zero* backoff, so against a fast-returning transient (e.g. a 502 in ~200ms) all attempts landed inside the same blip and the pipeline went to terminal `error` before any step ran (no status, no notification — silently stalling prod deploys / sync-back). Added exponential backoff (`forgeRetryBackoff`, 250ms base) between attempts, abandoned immediately on context-cancel. **(2) Hook-parse (#321):** the webhook-synchronous forge calls in `Hook()` (`ListFiles`/`ListTags`/`GetCommit`/`CompareCommits`) had zero retry, and any error was flattened to a `400` that GitHub treats as "never retry" — permanently dropping the trigger. Added a shared bounded-retry helper (`retryHookForgeCall` + `isRetryableForgeError`, 3 attempts, linear backoff kept well under the ~10s webhook-delivery timeout) that retries only transient failures (5xx, 429, typed rate-limit, network/timeout) and leaves permanent 4xx untouched; when a transient survives all attempts it is wrapped in `forge_types.ErrTransientForge`, which `hook.go` now translates to a retryable **503** (so GitHub redelivers) instead of a permanent 400. One classification pattern applied at both seams rather than N bespoke retry loops.
- fix: the idle local/gRPC agent no longer wedges on a `too_many_pings` GoAway — coordinate gRPC keepalive across agent and server (#312). Confirmed live 2026-07-11: the `d3ci42-local` agent (gRPC transport, mostly idle — it only runs occasional host-pinned `wake`/`cleanup`) received `GoAway ENHANCE_YOUR_CALM "too_many_pings"` from the server's keepalive-enforcement, after which its **workflow-RPC channel** (`Next`/`wait`/`update`) wedged on `DeadlineExceeded` **while its heartbeat/registration path stayed alive** — so `/api/agents` showed it connected (`last_contact` fresh) and it kept **claiming** workflows it could no longer **report**, leaving `wake` **skipped** and every `pts-build` bake wedged (#510/#511 on a server restart; #515 on a bare 15:00 GoAway with *no* restart — the trigger is the GoAway, not the restart). Three coupled defects: **(1)** the server's `KeepaliveEnforcementPolicy` set no `PermitWithoutStream`, so it rejected keepalive pings from a connected-but-idle agent; **(2)** both `WOODPECKER_KEEPALIVE_MIN_TIME` (server) and `WOODPECKER_KEEPALIVE_TIME` (agent) defaulted to **0**, so there was no coordinated floor/interval; **(3)** a latent flag-name bug — `agent.go` dialed with `c.Duration("grpc-keepalive-time")`/`"grpc-keepalive-timeout"`, names **defined nowhere**, so the client keepalive was silently `{Time:0, Timeout:0}` regardless of flag or env. Fix: both sides now set `PermitWithoutStream: true` (tolerate/keep idle pings so a dead connection is detected and reconnected during idle), the flag defaults are pinned as coordinated constants in `shared/constant` (`GRPCKeepaliveTime=30s` agent, `GRPCKeepaliveMinTime=10s` server) with the load-bearing invariant **agent interval ≥ server floor** (else a conforming agent ping is "too fast" and the GoAway returns), and `agent.go` reads the real flag names (`keepalive-time`/`keepalive-timeout`) so config actually reaches the dial. `TestGRPCKeepaliveInvariant` locks the interval-≥-floor + both-positive invariant (0 was the original defect); `TestKeepaliveFlagsWired` locks that the dial's flag names exist and default to the constant (guards the name regression). The wiring (`cmd/agent`, `cmd/server`) is on the existing `^cmd/` coverage exemption; `shared/constant` is pure declarations. Defense-in-depth remains open for restarts that break the channel some *other* way — a deploy-driven restart bounces the agent too (verified version-matched, no wedge on the pts.516 deploy), so the residual risk narrows to server-only restarts (e.g. the scaler#1753 watchdog); a follow-up teardown+redial-on-repeated-DeadlineExceeded recovery lever is noted on the issue.
- fix: config loading no longer fetches — and no longer fails on a transient error from — files that can't be a pipeline config (#316). The GitHub `Dir()` adapter listed `.woodpecker/`, then **fanned out a concurrent content fetch for every entry**, including `*.disabled` files and READMEs, and only *afterward* did `filterPipelineFiles` discard the non-`.yaml`/`.yml` ones — so we fetched content we were about to throw away, and because the fan-out is **first-error-wins with no retry**, a single transient GitHub 502 on one of those throwaway files failed the entire config load (`could not load config from forge`), erroring the whole pipeline before any step ran. Diagnosed live 2026-07-11: pipelines errored repeatedly while GitHub was "operational" and the shared PAT was at 4997/5000 — the 502s were on `links.yaml.disabled` / `securityscan.yaml.disabled`, content we never needed. Low request volume gives no protection because the exposure is per-config-load (N concurrent calls, one 502 is enough), not per-hour. Fix (cut at the source, **not** retry — adding retry would be the tolerance-widening our own discipline forbids): filter the directory listing to `.yaml`/`.yml` **before** the content fan-out, so a non-config entry is never fetched and can never fail the load. The predicate now lives once in `server/forge/types.IsPipelineConfigFile` and is shared by both the adapter's pre-fetch filter and the config service's post-fetch `filterPipelineFiles`, so they cannot drift and silently drop a valid config. Behaviour is identical for a folder of valid config. `IsPipelineConfigFile` + `filterPipelineFiles` at 100% per-file; new `TestDirFetchesOnlyPipelineConfigFiles` (go-github-mock) asserts a mixed folder fetches only the two yaml files and the `.disabled`/README entries never hit `File()`; `github.go` stays on the existing forge-adapter coverage exemption.

- fix: `GET /api/repos/{repo_id}/logs/{number}/{stepID}` no longer returns a silent empty 404 when given a step's per-pipeline number (#313). The step path segment is documented only as "the step id"; the web UI passes the step's **global DB id** (`StepLoad`), but a human or CLI/debug tool naturally passes the **per-pipeline step number (pid)** — the same mental model as the pipeline `number` earlier in the same path. `StepLoad(pid)` then either misses (`ErrRecordNotExist`) or resolves a step in a *different* pipeline, and the handler returned a bare 404/400 whose body was empty — indistinguishable from "this route does not exist" (the fork's #27 unknown-path disease), which sent the reporter down a "route-registration regression" path and left SSH+`sqlite3` hand-querying `log_entries` as the only way to read step output. A DB id that belongs to another pipeline is now reinterpreted as this pipeline's pid rather than 400ing. New `TestGetStepLogs` covers all five paths (DB-id hit, pid fallback, foreign-DB-id→pid reinterpretation, descriptive-404 body assertion, invalid-id 400); `pipeline.go` stays on the existing REST-handler-aggregate coverage exemption.
