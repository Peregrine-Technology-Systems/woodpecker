# Release Notes

## Unreleased

- docs+fix: write down the `ci-events` Pub/Sub pipeline-event contract and fail-close on empty event types (#264). Scaler's subscriber was rejecting every pipeline lifecycle event from this fork: it expected a nested `data.pipeline: {id, status, event, branch, repo_id}` struct, but the fork has always emitted a **flat** payload (`data.pipeline` is the pipeline *number* as an `int64`, with `status`/`branch`/`event` as flat siblings; `schema_version "1.0"`, deliberately webhook-sidecar-compatible). The shape was never written down, so it drifted into a consumer assumption. Adds [`server/plugin/gcppubsub/CONTRACT.md`](server/plugin/gcppubsub/CONTRACT.md) as the authoritative wire contract (co-located with `format.go`/`publisher.go` since the fork is the publisher): the flat envelope + `data` schema, the message attributes, and the full event-type table with the two subscriber gotchas — the terminal-success event is **`pipeline.success`, not `pipeline.completed`** (internal `EventPipelineCompleted` maps to the wire string `pipeline.success`), and there is **no `pipeline.running`** event. Referenced from `format.go` and `docs/ARCHITECTURE.md`. Also adds the **fail-closed counterpart** for the observed empty-`type=` messages: `OnEvent` now refuses to publish an event whose resolved wire type is empty (`ErrEmptyEventType`) instead of putting a typeless message on the topic — proving structurally that the empty-type and `pipeline.deploy_completed` events seen downstream originate from a *different* publisher on the shared topic (infra deploy script), not this fork. Tests cover both the empty and whitespace-only type paths and assert nothing is published.

- fix: backend is free-form; drop the `backend`+`tier` cross-rule; pin hosts on `backend`, not `tier` (#261, follow-up to #255). #255 encoded a fleet topology that had already shifted: it assumed `backend: local` ⟺ the tierless server box, so it rejected `backend: local` + any `tier`. But post peregrine-infrastructure#1357 the whole fleet honestly advertises `backend: local` (Docker-less native execution), making `backend: local + tier: spot` the **normal** case (native step on a spot VM) — the validator was rejecting the ~90% pattern. The three label dimensions are now orthogonal: `platform` = OS/arch, `backend` = execution environment (free-form — engine → flavor → a `local-<host>` host pin), `tier` = scaling class only. `ValidateLabelCombination` now governs **only `tier`** (must be in `KnownTiers`); `backend`/`platform` values are never gated. A specific host is pinned via `backend: local-<host>` (exact-match isolates it from generic `local` work both ways), e.g. the server box advertises `backend: local-d3ci42` — **not** a tier. `tier: local` stays rejected (host-identity is not a scaling class; the prior widespread `tier: local` convention migrates to `backend: local-<host>` for box-local work or a real `tier` for the rest — see #261 for the recipe). Lesson worth keeping: a validator must encode *structural* legality (a tier typo no agent will ever advertise), not a point-in-time fleet composition — and under scale-to-zero "no agent satisfies this combo" is unprovable at submit (the satisfying VM may not be booted yet). Tests flip the `backend:local+tier` cases to legal and lock `backend`-values-never-gated; `tier: local` remains the illegal fixture.

- feat: reject incompatible label combinations at queue acceptance instead of stalling silently (#255). Woodpecker matches a task's labels against agent labels (`server/rpc/filter.go`) — every non-empty task label must be present on an agent — but never checks at submit time whether *any* agent could satisfy the set. Rules: a `tier` value must be one of the known GCP VM classes (`spot`/`ondemand`/`n2`/`integration-test`), and `backend=local` may not be combined with any `tier`. Skipped workflows aren't validated (they never queue). Adds the `LabelFilterTier` const (replacing the hardcoded `"tier"` in the deploy-routing filter) and documents the taxonomy in `docs/ARCHITECTURE.md`. Same falcon-discipline shape as silent-OK detection: the queue no longer reports a task accepted without proving an agent can run it. Re-filed from peregrine-infrastructure#3087 (terraform doesn't own the server source — this fork does).

- fix: stop the agent from recycling its identity every ~45 min to refresh its token (#252). The #116 "proactive token refresh" goroutine in `cmd/agent/core/agent.go` exited the process at 75% of the JWT lifetime when idle — deleting `agent.conf` and `log.Fatal()`-ing so systemd restarted it with a fresh registration under a **new agent_id**. That scheduled identity churn was the upstream trigger behind the straddler-stranding family (#243/#246/#248): a dependent workflow that became dispatchable around the ~45-min recycle was orphaned onto the vanished agent_id and, on the gRPC/local transport (no #208 grace, fail-safe #246 reclaim), waited the full 15-min `TaskTimeout` while the pipeline timed out first — `skipped`/`killed` (confirmed repro: peregrine-infrastructure pipeline 5324). It was also redundant: the gRPC `AuthInterceptor` (`agent/rpc/auth_interceptor.go`) already refreshes the JWT **in place** every 30 min (< the 1 h lifetime) keeping the same agent_id and connection, and the WS transport authenticates with the durable agent token (no short-lived JWT to expire). So token expiry was already prevented on both transports without churning identity — #116 only ever produced the harmful recycle. Fix: delete the proactive-restart block (no replacement needed). Added `agent/rpc/auth_interceptor_test.go` asserting the interceptor refreshes the access token in place across scheduled refreshes while the agent_id stays constant — the property that makes the deletion safe. Archaeology: #116 was a stopgap whose own revert commit (`da4c9aae2`) described in-place "heartbeat refresh" as a future fix to build, unaware the upstream interceptor already did exactly that; the identity-destroying `os.Remove(conf)` was copy-pasted from the unrelated stale-conf recovery path (#101). #248 (transport-agnostic liveness reclaim) remains as defense-in-depth for unavoidable recycles (spot preemption, crashes).

- fix: owner-liveness reclaim must fail SAFE — never kill a `backend: local` / gRPC-transport agent's steps at t+0s (#246, regression from #243/#244 in pts.429). The #244 reclaim keyed on "is the owning agent absent from the connected set?" — but that set (`server/api` connected-agent registry) is populated only by the WebSocket transport (`ws_agent.go` `handleRegister` → `markAgentConnected`). Agents on the gRPC transport (`WOODPECKER_AGENT_TRANSPORT=grpc`, the default — including the co-located `d3ci42-local` `backend: local` agent) register through `server/rpc` `RegisterAgent`, which never touches that registry. So every gRPC agent read as "not connected" ⇒ dead, and the queue fired `ReleaseAgentTasks` on its running tasks at the first ~100ms dispatch tick: the clone step was marked `killed` at t+0s and the agent's own state updates were rejected with `FailedPrecondition … state=killed`, hanging the workflow in `partial`. This jammed the `tier: local` infra self-management pipelines (`apply-agent-image`, `deploy-server-config`) on d3ci42 — the second-order cause behind a CI control-plane jam (peregrine-infrastructure#2955/#2957). It also means #244 never actually delivered #243's fix for the local agent (the only agent #243 was about), since that agent was never in the registry to begin with. Fix: invert the oracle from fail-dangerous "absent ⇒ dead" to fail-safe "positively-observed-disconnected ⇒ dead." A new `IsAgentKnownDisconnected` keys only on agents whose #208 WS reconnect grace explicitly expired (`markAgentDisconnected`); an agent whose liveness was never tracked (any gRPC/local agent) is treated as ALIVE and falls back to the 15-minute `TaskTimeout` lease, exactly as before #244. The queue interface method is renamed `SetAgentLivenessFn` → `SetAgentReclaimFn(knownDead, reclaim)` to make the contract honest, and the known-disconnected set is dropped on reconnect and after a reclaim releases the agent's tasks so it stays bounded. The `running_dead_owner` gauge now counts only positively-known-dead owners (previously it over-counted every gRPC agent's tasks). The reclaim survives only as a narrow safety net for the documented post-grace-release race on WS agents; the gRPC/local recycle path is correctly left to `TaskTimeout` until a transport-aware liveness signal exists. A clean server restart does NOT clear the symptom — it is a code path, not accumulated state (the in-memory registry resets empty on restart, so the bug re-arms). 100% coverage on the changed queue/api logic; `cmd/server/setup.go` wiring exempt.
- feat: owner-liveness reclaim + orphan-workflow metrics for tasks stranded by an agent recycle (#243). When a `d3ci42-local` agent recycled mid-pipeline and came back under a *new* agent_id (#77), the deferred `ReleaseAgentTasks` (#208) for the *old* id reclaimed nothing, and a workflow whose `depends_on` parent had run on the old agent could sit undispatched until the 15-minute `TaskTimeout` lease — then time out into `skipped` while the pipeline went `killed`, a worse-than-nothing recovery. The dispatcher's only "agent died" signal was that TTL. New: a connected-agent registry in `server/api` (`markAgentConnected` on register, `markAgentDisconnected` when the #208 grace expires) lets the queue ask, every ~100ms dispatch tick, whether a running task's owning agent still has a live connection. If not, it fires `ReclaimAgentTasks` within one tick instead of waiting the lease — reusing `ReleaseAgentTasks`' safe re-queue-vs-kill partition, so a step that did real work is killed (never blindly re-run, no duplicated partial deploy) and a claimed-but-no-work task is re-queued for the next agent. This also closes the post-release assignment race (a task that lands in `q.running` for a dead id *after* the one-shot grace release). Liveness is "has a live WS connection," not "is idle," so a busy agent running a quiet step is never mistaken for dead; reclaim is deduped per agent and throttled per `reclaimRefireInterval`. New observability (alert on sustained > 0): gauge `woodpecker_orphaned_workflows{state="running_dead_owner"|"pending_dispatchable"}` sampled each tick, and counter `woodpecker_orphaned_workflows_reclaimed_total` (gauge has no `_total` suffix by Prometheus convention; the cumulative reclaim count is the separate counter). `pending_dispatchable` covers the issue author's read (a deps-satisfied task aging in `q.pending`) since static analysis could not distinguish that from the running-on-dead-owner manifestation. 100% coverage on the new queue/api logic; `cmd/server/setup.go` wiring exempt. The agent reporting `v3.13.0-pts.agent` (literal, unsubstituted) is a separate ci-agent image build-template bug filed cross-repo against peregrine-infrastructure (no `pts.agent` literal exists in this repo — pts-build.sh versions server and agent identically).

- test: lock the Pub/Sub `event_type` attribute ↔ payload `type` coupling (#234). The GCP Pub/Sub plugin already sets the `event_type` message attribute to the CloudEvents pipeline type and marshals the same value into the payload `type` (so they match by construction), for every lifecycle event — `pipeline.created`/`pending`/`started`/`success`/`failed`/`killed`/`superseded` and `step.completed`. - fix(security): a step's `environment:` can no longer forge reserved `CI_*` metadata (#236). The compiler seeded step env with trusted server metadata and then let the user's `environment:` blind-overwrite it (`ParamsToEnv` with no reserved-key guard), so a pipeline could set `CI_REPO`/`CI_REPO_NAME`/`CI_REPO_ID`/`CI_COMMIT_SHA`/… to arbitrary values. On the local backend those flowed straight to the step process, and any consumer trusting them for authorization — e.g. an agent hook selecting per-repo GitHub deploy keys off `CI_REPO_NAME` (peregrine-infrastructure#2919), or the #235 outcome-verification commit check — became attacker-controllable. Fix at the source (compiler, all backends): the `CI_*` namespace is server-authoritative — snapshot it before applying the user's `environment:` and re-assert it after, so user config may add new vars but can never override reserved metadata. Non-`CI_` user env is unaffected. (The issue's local-backend `notAllowedEnvVarOverwrites` proposal is not the right layer — the local backend has no trusted `CI_REPO` source of its own, unlike `CI_WORKSPACE`'s workspace state, so dropping the key there would just blank it; the compiler is where the trusted value lives.)

- fix: a spurious cancel can no longer kill a workflow whose every step already succeeded (#230, #232). `UpdateWorkflowStatusToDone` previously did `if state.Canceled { State = Killed }` unconditionally — so a SIGTERM (scaler scaling down a dedicated on-demand VM, or a spot preemption) or any late cancel that arrived *after* all steps reached `success exit_code=0` retroactively flipped the workflow to `killed` (error `"Canceled"` from the agent path, `""` from the server path). This produced phantom failures: green deploys paged on-call, dashboards showed deploys as un-validated, and downstream `depends_on` work was skipped. Root cause: the agent (`runner.go`) correctly reports `Canceled=true` when its workflow context is canceled, but the server collapsed that to `killed` without consulting child-step outcomes. Fix: on `Canceled`, only force `killed` when a child step is itself `killed` (the authoritative signal a running step was cut off — a canceled running step is recorded as `StatusKilled` via its own update) or when the workflow has no recorded steps; otherwise compute the honest status from the steps and clear the spurious `"Canceled"` error. `rpc.Done` now propagates the reconciled state to queue dependents instead of blindly killing them. Mirrors the disconnect-path guard from #168, which the `Done` path never received; covers `ci`/`promote`/`deploy` alike. 100% coverage on `workflow_status.go`.

- feat: outcome-verification on step kill — server-side HTTP proof-query (#235 F1+F2, Option A; peregrine-ci-scaler#1326/#1328). A step killed mid-execution can declare a read-only proof-query that the server runs to check whether its work actually landed; on a match the killed step is reconciled to success instead of failing the pipeline. Two forms: the `kind: deploy` shorthand (`verify_url` + `verify_expect_commit`, the CLAUDE.md deploy /version contract) and an explicit declarative `verify:` block (`when_killed`, `url`, `expect_commit`, `expect_status`). The server (not an agent) issues a single `GET`, checks the status (default 200) and, when an expected commit is given, compares the response's `commit` JSON field by 7-char prefix. Wired into both the agent-`Done` path and the agent-disconnect path (`ReleaseAgentTasks`, covering "agent disconnected mid-deploy but the deploy landed" — scaler#1055). Composes with the #230/#232 invariant: flipping the only killed step to success makes the workflow succeed. Carried as a `verify` JSON column on the `steps` table (migration 030) so it is readable at kill time without the by-then-deleted queue task; validated by the YAML schema (`kind: deploy` requires `verify_url`; the shorthand and `verify:` block are mutually exclusive; `when_killed` must be true; URL must be http(s)). Arbitrary-command (ssh/gcloud) verify probes that need a fresh agent are deliberately out of scope here and filed as a follow-up. New `ReconcileVerifiedKilledSteps` (server/pipeline/verify.go, 98%); `convertVerify` 100%.

- feat: widen the agent-disconnect re-queue predicate to recover "ack'd then vanished" workflows (#235 F3, peregrine-ci-scaler#1327). Previously `ReleaseAgentTasks` re-queued only when no step had `Started`; a step stamped `Started` but with no log output and no real exit code (e.g. a spot VM preempted seconds after dispatch-ack) landed in the kill path and was unrecoverable. The predicate now keys on whether a step did *observable* work: a step is "real work" (forcing kill, to avoid duplicating side effects like a partial deploy) only if it succeeded, returned a positive exit code, or emitted at least one log line. Workflows whose steps did no real work are re-queued, and their phantom-started steps are reset to pending so the new agent's updates aren't rejected as terminal-state transitions. Conservative by design: any genuine execution signal keeps the kill path. New `stepDidRealWork`/`resetWorkflowForRequeue` helpers; covered by `release_agent_tasks_test.go`.
