- fix: serialize all SQLite write operations through a single drain goroutine to eliminate SQLITE_BUSY "database table is locked" errors under concurrent load (#55). Root cause: concurrent HTTP handlers (pipeline status updates, webhook ingestion, agent registrations) raced on the SQLite writer lock, producing lock errors that caused the server to freeze and triggered cascading healthcheck up/down Slack alerts. Fix: `writeQueue` type with a buffered channel (depth 256) and a single drain goroutine. All 33 write methods across agent, config, cron, forge, log, org, permission, pipeline, redirection, registry, repo, secret, server_config, step, task, user, and workflow are wrapped in `s.wq.serialize(func() error { ... })`. Read methods bypass the queue entirely (SQLite WAL allows concurrent readers). Non-SQLite drivers: `wq` is nil and `serialize()` calls the fn directly with zero overhead. Integration test `TestWriteQueue_ConcurrentWrites_NoLockErrors` exercises 50 goroutines × 10 writes (500 total) on a file-based SQLite database, verifies all complete without error, and reads back all 500 values for consistency. Observed in production 2026-05-04 ~20:17 UTC: `database table is locked: pipelines` under simultaneous deploy + agent registrations + pipeline completions.

- Fix: server startup no longer logs "no sqlite3 file found" when the SQLite DB exists at the configured path (#41). Root cause: `checkSqliteFileExist` was `os.Stat`-ing the raw DSN, which on Woodpecker's normal startup looks like `file:/var/lib/woodpecker/woodpecker.sqlite?_busy_timeout=...&_journal_mode=WAL&...` — `os.Stat` correctly reports ENOENT for that literal name, even though the actual file at `/var/lib/woodpecker/woodpecker.sqlite` exists and is opened successfully two lines later. - Fix: stop posting `errored` status to GitHub for workflows killed by agent disconnect (#44).
